# Stack Detection Protocol

Detection is evidence collection, not filename guessing. Build a stack record before planning. Scan the repository as a graph, not only its root.

## Scan boundaries

Exclude generated/vendor/cache trees unless the task explicitly concerns them:
`.git`, `node_modules`, `.venv`, `venv`, `target`, `build`, `dist`, `out`, `vendor`, `.gradle`, `coverage`, `.next`, `.turbo`, `__pycache__`.

Inspect all repository modules/workspaces. Detect roots from manifests and workspace configuration, then associate source/config files with the nearest root.

## Detection dimensions

For each repository/module, detect independently:

1. Language: Java, Kotlin, Groovy, JavaScript, TypeScript, Python, Go, Rust, C#, F#, PHP, Ruby, Elixir, Dart, Swift, Objective-C, C/C++ and other clearly evidenced languages.
2. Runtime/toolchain: JVM/Java version, Node/Bun/Deno, Python, Go, Rust toolchain, .NET SDK/runtime, PHP, Ruby, Elixir/Erlang, Dart/Flutter, Swift/Xcode, etc.
3. Build/package manager: Maven, Gradle, npm, pnpm, yarn, bun, pip/uv/Poetry/PDM/Hatch, Cargo, Go modules, NuGet/MSBuild, Composer, Bundler, Mix, pub, SwiftPM, CMake, Meson and others when evidenced.
4. Framework: identify concrete frameworks using dependency, plugin, source import, config, and CLI fingerprints.
5. Application role: backend API, web frontend, CLI, worker, library, mobile, desktop, infrastructure, data/ML, monorepo/package workspace.
6. Material subsystems: database/ORM, messaging, HTTP clients, auth/security, caching, observability, migrations, serialization, templating, frontend routing/state, container/orchestration.
7. Test tooling: JUnit/TestNG, pytest, Jest/Vitest, Playwright/Cypress, Go test, cargo test, xUnit/NUnit, RSpec/Minitest, ExUnit, Flutter test, etc.
8. Deployment/infrastructure: Docker/Compose, Kubernetes/Helm, Terraform/OpenTofu, serverless, CI providers, buildpacks, cloud-specific config.
9. Version constraints: lockfiles, wrappers, toolchain files, runtime declarations, BOMs/catalogs and dependency manifests.

## Evidence hierarchy

Prefer strong evidence in this order:

1. project configuration that explicitly names the framework/plugin
2. dependency declaration or resolved dependency
3. source import/annotation/attribute/API usage
4. framework-specific directory/config convention
5. framework CLI/config generated by the framework
6. filename-only heuristic

Use confidence levels:
- `high`: at least one strong signal plus corroboration, or multiple strong signals
- `medium`: one strong signal without corroboration, or several weaker signals
- `low`: only weak heuristics

Never turn a low-confidence heuristic into a precise framework claim.

## Framework fingerprints

### Java/Kotlin/Groovy
Look for Spring Boot, Spring MVC/WebFlux/Security/Data, Quarkus, Micronaut, Ktor, Vert.x and Android/AGP fingerprints. For Spring Boot, load `spring-boot-detection.md`.

### JavaScript/TypeScript
Check package dependencies, package scripts, workspace config and framework config for Next.js, React, Vite, Angular, Vue, Nuxt, Svelte/SvelteKit, Remix, Astro, NestJS, Express, Fastify and other concrete frameworks. Distinguish language from runtime and framework.

### Python
Check `pyproject.toml`, lockfiles and imports/config for Django, Flask, FastAPI, Starlette, Litestar, Pydantic, SQLAlchemy and major task/data frameworks. Detect the actual package manager and build backend when possible.

### Go
Start from `go.mod`/`go.work`; identify web frameworks such as Gin, Echo, Fiber, Chi, stdlib `net/http`, and other material libraries from imports/dependencies.

### Rust
Use `Cargo.toml`/lockfile and imports to distinguish Axum, Actix Web, Rocket, Tokio and related runtimes/libraries.

### .NET
Inspect `.sln`, `.slnx`, `.csproj`, `.fsproj`, Directory.Build.* and SDK declarations. Distinguish console/library, ASP.NET Core, Blazor, MAUI and test frameworks from project SDK/package/source evidence.

### PHP/Ruby/Elixir/Dart/Flutter/Swift/C/C++
Use native manifests/config plus source imports and generated project structure. Examples include Laravel/Symfony, Rails/Sinatra, Phoenix, Flutter/Dart, SwiftPM/Xcode, CMake/Meson and their major framework dependencies.

## Monorepo rules

Detect workspace roots and report:
- repository root
- module/package roots
- language/framework per module
- shared toolchain/config
- cross-module dependencies
- whether the requested change crosses module boundaries

Do not collapse a mixed repository into a single “primary framework” if multiple applications or packages materially differ.

## Negative evidence and ambiguity

A manifest alone does not prove a framework. Example: `pom.xml` proves Maven, not Spring Boot. `package.json` proves Node package metadata, not React or Next.js. `pyproject.toml` proves Python project configuration, not Django.

When framework evidence conflicts, preserve both candidates, identify the conflict, and resolve using dependency/source evidence before implementation.

## Detection record

Produce a compact record:

```text
repository_type: single|monorepo|workspace|multi-module|unknown
modules: ...
languages: ...
runtimes: ...
build_tools: ...
frameworks: ...
application_roles: ...
material_subsystems: ...
test_tools: ...
infrastructure: ...
versions: ...
confidence: ...
evidence: path -> signal
ambiguities: ...
research_profiles: ...
```


## Detection corrections

- Host binaries never establish project identity. Use repository-declared files, wrappers, lockfiles, CI, imports, and module structure first.
- Nested dependency/generated directories must be pruned at every depth.
- A dependency appearing in a monorepo does not prove that every package/module uses it. Preserve path/module scope.
- Distinguish framework presence from primary application framework. Do not silently collapse multi-framework repositories.
- Detection output is advisory evidence; the agent must reconcile contradictory signals before routing.
- Record missing expected tooling separately from “framework not detected”. A missing local Maven/Gradle/.NET tool does not mean the project is not a JVM/.NET project.
